# On-chain deposits

NSpark supports two flavours of on-chain deposit:

1. **Single-use deposit address** — one address, one expected deposit,
   claimed once into a leaf with the exact deposit value.
2. **Static deposit address** — reusable address; the user can drop
   multiple UTXOs into it, each claimed individually via the SSP for a
   quoted credit amount.

Both flavours follow the same conceptual flow: generate address → fund
on-chain → wait for confirmations → claim. **The claim step is what
turns the on-chain confirmation into a spendable Spark leaf.**

> Single-use deposits use `ClaimDepositAsync`, static deposits use
> `ClaimStaticDepositAsync`. The two call signatures and the resulting
> credit semantics are different — see below.

## Single-use deposit

### 1. Generate a deposit address

```csharp
using NSpark;
using NSpark.Services;

var deposit = await wallet.GetDepositAddressAsync();
Console.WriteLine(deposit.Address);   // bc1p... taproot address on mainnet
```

`GetDepositAddressAsync` allocates a fresh leaf id, derives the
per-leaf signing key, and asks the Signing Operators to generate the
shared address. The returned `DepositAddress` contains:

- `Address` — the bech32m P2TR address.
- `LeafId` — the leaf that will materialize when you claim. Persist it
  if you want to track which deposit corresponds to which on-chain UTXO.
- `UserPublicKey` — your contribution to the FROST address.
- `VerifyingKey` — the FROST group verifying key.

### 2. Pay into it (on-chain, external)

The payer sends Bitcoin to `deposit.Address`. NSpark doesn't broadcast
this transaction — the user uses any L1 wallet (Sparrow, Electrum, BDK,
etc.) and provides the resulting txid.

### 3. Wait for confirmations

Spark requires the funding transaction to be confirmed before claim.
Typically you'd let your application's UI poll mempool.space or your
own Bitcoin node until the user-supplied txid hits enough confirmations
for your risk model.

### 4. Claim

```csharp
await wallet.ClaimDepositAsync(
    depositTxId: "abc123...",   // 64-hex transaction id
    vout: 0,                    // output index of the deposit
    ct: cancellationToken);
```

`ClaimDepositAsync` fetches the raw transaction, validates the output
matches the address NSpark generated, and constructs the Spark tree.
After it returns, the leaf is in `AVAILABLE` state and shows up in
`SatsBalance.Available`.

`ClaimDepositAsync` returns `Task` (not `Task<…>`) — the leaf id was
already returned to you in step 1.

### Querying unused deposit addresses

If your application crashes or restarts between step 1 and step 4, you
can recover the outstanding addresses:

```csharp
var unused = await wallet.QueryUnusedDepositAddressesAsync();
foreach (var entry in unused)
{
    Console.WriteLine($"{entry.Address}  leafId={entry.LeafId}");
}
```

This is the list of every single-use address generated by the wallet
that hasn't been claimed yet. Static deposit addresses are NOT in this
list — they're never "used up" so they don't have an unused/used
distinction.

### Inspecting UTXOs at an address

```csharp
var utxos = await wallet.GetUtxosForDepositAddressAsync(
    address: deposit.Address,
    excludeClaimed: true);

foreach (var u in utxos)
{
    Console.WriteLine($"{u.Txid}:{u.Vout}");
}
```

This is the SO-side view of what's been observed on-chain at that
address — useful for surfacing the txid to the user before they ask.

## Static deposit

Static deposits are addresses that can receive **many** UTXOs. Each
incoming UTXO is claimed individually via the SSP, which quotes a credit
amount (typically the UTXO value minus the SSP's deposit fee) and signs
that quote. The wallet co-signs and submits the claim.

### 1. Generate the static address

```csharp
var staticAddr = await wallet.GetStaticDepositAddressAsync();
Console.WriteLine(staticAddr.Address);   // reusable bc1p...
```

The wallet derives a single static-deposit key (`m/8797555'/account'/3'/2^31`),
so `GetStaticDepositAddressAsync` is **deterministic** — the same wallet
returns the same address on repeated calls. Persist it as a long-lived
deposit address for a given user account.

### 2. Pay into it (one or many times)

Multiple UTXOs are fine. Each one is claimed separately.

### 3. Get a fee estimate (optional)

```csharp
var quote = await wallet.GetDepositFeeEstimateAsync(
    transactionId: "abc...",
    outputIndex: 0);

Console.WriteLine($"Would credit {quote.CreditAmountSats} sats");
```

The credit amount reflects the SSP's fee and the actual UTXO value.

### 4. Claim

```csharp
var transferId = await wallet.ClaimStaticDepositAsync(
    transactionId: "abc...",
    outputIndex: 0);
```

This returns a transfer id (not a leaf id) because static-deposit
claims funnel through the SSP's Spark transfer mechanism. The credited
amount arrives as a pending transfer — **which you then claim**:

```csharp
await wallet.ClaimPendingTransfersAsync();
```

Yes, that's two claim steps for a static deposit:

1. `ClaimStaticDepositAsync(txid, vout)` — co-sign the SSP quote;
   produces a pending Spark transfer.
2. `ClaimPendingTransfersAsync()` — materialize the transfer as a
   spendable leaf.

This mirrors how Lightning receives work (the SSP creates a pending
transfer, you claim).

### Refunding a static deposit

If you change your mind before claiming, you can refund the UTXO back
to an on-chain address:

```csharp
var refundTxid = await wallet.RefundStaticDepositAsync(
    transactionId: "abc...",
    outputIndex: 0,
    destinationOnChainAddress: "bc1q...",
    satsPerVbyte: 8);
```

`RefundStaticDepositAsync` builds a Taproot spend transaction back to
the destination address, signs it with the static-deposit FROST round,
and broadcasts via the configured Bitcoin RPC endpoint (mempool.space
by default). The returned id is the **on-chain** refund transaction id.

> **One refund per UTXO.** After refund, the UTXO is spent on-chain and
> cannot be claimed.

## Differences at a glance

|                                  | Single-use                         | Static                                       |
| -------------------------------- | ---------------------------------- | -------------------------------------------- |
| Address per wallet               | One per `GetDepositAddressAsync`   | One total (deterministic from key)           |
| UTXOs per address                | Exactly one                        | Many                                         |
| Fee on receive                   | None (just L1 fees)                | SSP fee (subtracted from quote)              |
| Claim API                        | `ClaimDepositAsync(txid, vout)`    | `ClaimStaticDepositAsync` + `ClaimPending…`  |
| Result                           | Leaf with exact UTXO value         | Spark transfer with quoted credit            |
| Refund?                          | No (claim or wait)                 | Yes — `RefundStaticDepositAsync`             |
| Recovery list                    | `QueryUnusedDepositAddressesAsync` | n/a (always the same address)                |

## Event-driven deposit claim

The event stream surfaces `DepositConfirmedEvent` when the SOs detect
the funding tx confirmed. The wallet still has to call the appropriate
claim method:

```csharp
await foreach (var evt in wallet.SubscribeEventsAsync(ct))
{
    switch (evt)
    {
        case DepositConfirmedEvent deposit:
            logger.LogInformation("Deposit confirmed for tree {TreeId}", deposit.TreeId);

            // For single-use: identify the (txid, vout) and:
            //   await wallet.ClaimDepositAsync(txid, vout, ct);
            // For static: use ClaimStaticDepositAsync + ClaimPendingTransfersAsync.
            break;
    }
}
```

The `TreeId` on the event maps to a leaf id you can match against your
own tracking — store the (txid, vout, leafId) tuple at address-
generation time.

## Errors

| Exception                       | Cause                                                          |
| ------------------------------- | -------------------------------------------------------------- |
| `SparkDepositException`         | SO-side failure (e.g. tx not yet confirmed, unknown output).   |
| `SparkConnectionException`      | gRPC / HTTP transport problem.                                 |
| `SparkAuthenticationException`  | SO or SSP rejected wallet identity.                            |
| `SparkSignerException`          | FROST signing or key derivation failed locally.                |

See [`error-handling.md`](error-handling.md) for the full taxonomy.
